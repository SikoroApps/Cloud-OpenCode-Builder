# Phase 7 — Image generation integration

Phase 7 implements the second advanced feature from `README.md` ("Image generation integration") and
`docs/BUILD_ORDER.md`. It uses a free, keyless image-generation provider and stores the result through
the Phase 6 image pipeline, so generated assets are owner-scoped and available to the Android client.

## Status

**COMPLETE AND LIVE-VERIFIED** against the free Pollinations image endpoint on 2026-11-24.

## Implemented

### Backend

- `POST /api/images/generate` accepts `{ "prompt": "...", "size": 512|768|1024 }` and optional
  `projectId`.
- Prompt length is capped at 2,000 characters. Sizes are restricted to a fixed allowlist; arbitrary
  dimensions are rejected with `400 invalid_image_size`.
- The provider host is fixed (`https://image.pollinations.ai/prompt` by default) and the prompt is
  URL-encoded. There is no user-supplied URL, so the endpoint cannot be used as an SSRF proxy.
- The provider request has a 60-second timeout, an `Accept: image/*` header and `safe=true`.
- Responses must have an image content type, valid image magic bytes, non-zero length and at most
  10 MiB. Errors map to `502 image_generation_failed`.
- Generated bytes pass the same MIME/size/path validation as uploads, are hashed with SHA-256 and are
  persisted to the same owner-scoped image table with `source = "generated"` and the original prompt.
- No paid service, API key or credential is required for the default provider. The provider base URL
  can be overridden with `IMAGE_GENERATION_URL` for a self-hosted compatible endpoint.
- `CLOUD_IMAGE_GENERATION_STUB=1` returns a deterministic 1×1 PNG for CI/offline tests; stub output is
  only used when explicitly enabled and is never presented as live evidence.

### Android client

- `CloudApiClient.generateImage(token, prompt, size, projectId?)` returns `CloudImage` metadata.
- Generated images can be displayed/downloaded through the authenticated
  `contentUrl` returned by the backend; the OAuth token is not placed in a URL.

## Tests

`cloud/tests/phase7-image-generation.test.ts` covers:

- the exact fixed provider URL, encoded prompt and size query parameters;
- a successful image response;
- upstream failure and non-image response rejection;
- invalid size rejection;
- generated bytes passing the upload validation/hash path.

The HTTP generation path is also covered by `cloud/tests/phase6-images.test.ts` with an injected
generator, proving persistence, ownership and prompt metadata without network dependence.

## Live evidence (2026-11-24)

A real backend was started with a temporary SQLite database and the default free provider:

1. `POST /api/images/generate` with prompt `a friendly blue cloud app icon, flat vector` and size
   `512` returned **HTTP 201**.
2. Stored metadata: MIME `image/jpeg`, `sizeBytes: 17277`,
   SHA-256 `62ac8e0945cea1df95145fd773e2e7a2163e9ce1919112974af52289c20f9169`.
3. A second backend restart, login with the same user, and authenticated
   `GET /api/images/<id>/content` returned **HTTP 200**, `content-type: image/jpeg`, 17,277 bytes and
   an independently computed SHA-256 matching the stored value exactly.
4. The generated file was written outside the repository under the harness temporary directory; no
   generated binary was committed.

This is a real upstream provider response, not a mock. The provider may rate-limit or be unavailable
in the future; the endpoint reports a safe `image_generation_failed` error in that case.

## Security review

- Fixed provider host and encoded prompt prevent SSRF and query injection.
- Image magic-byte validation prevents HTML/error pages being stored as images.
- Generated images inherit owner scoping and project ownership checks.
- No API key is required or logged.
- The Android client never receives a provider credential.
